# Implementation plan

Status, 2026-09-14: milestones 1 through 5 are implemented in this repository
and their gates pass. Milestone 6 is the admin's to run on the walzen test
cluster, and its steps are written out in
[.cortex/reports/2026-09-14-backup-controller-cluster-runbook.md](../.cortex/reports/2026-09-14-backup-controller-cluster-runbook.md).
Milestone 7, the infrastructure repository, is untouched.

Written for an agent starting from an empty repository with no memory of the
design conversation. Read [overview.md](overview.md) and
[architecture.md](architecture.md) first; this page is the order of work and
what proves each step.

## Before writing code

Confirm three things against the version of the library you are about to pin,
because the design rests on them and this plan was written from master rather
than from a tag:

| Check | Where |
| --- | --- |
| `RunControllerWithConfig` and `ProviderFunctionConfig` exist, with `PopulateFn`, `PopulateCompleteFn` and `PopulateCleanupFn` | `populator-machinery/controller.go` |
| the exact fields of `PopulatorParams`, particularly the prime claim and the data source object | the same file |
| the prime claim is created in the controller's namespace, named `prime-<uid>`, and carries `volume.kubernetes.io/selected-node` for a WaitForFirstConsumer class | the same file |

If any differs, say so before building around it rather than working around it
quietly.

## Milestone 1: the repository stands up

1. `go.mod`, a `flake.nix` dev shell holding go, golangci-lint, kustomize,
   kubectl, helm and yq, and an `.envrc` that uses it.
2. `.github/workflows/ci.yaml` running `go vet`, `go test -race`,
   `golangci-lint run` and `go build`.
3. A `Makefile` with the same four commands, so a person and CI run one thing.

Proof: CI green on an empty package.

## Milestone 2: the API

1. `internal/api/v1alpha1` with the `VolumeRestore` types from
   [api.md](api.md), deepcopy generation, and the scheme registration.
2. `config/crd` generated by controller-gen, with the validation rules api.md
   lists.
3. `config/samples` with a VolumeRestore and a claim that names it.

Proof: `kubectl apply --dry-run=server -f config/crd` on a cluster, then
applying a sample and reading it back.

## Milestone 3: the populator, against a fake

1. `internal/volsync`: build a ReplicationDestination from a VolumeRestore and a
   prime claim, and read completion from its status. Pure functions taking
   structs, no client.
2. `internal/populator`: the three callbacks, taking an interface for the
   Kubernetes operations rather than a concrete client.
3. Table tests over both, with a fake client. Cover the Secret copy, the naming
   from the claim UID, a destination that already exists, and a destination
   reporting a failed mover.

Proof: `go test ./... -race` green, and the tests name the cases above.

## Milestone 4: the binary

1. `cmd/backup-controller`: flags for kubeconfig, namespace, metrics endpoint,
   and the image name the library wants even in provider-function mode.
2. Wire `RunControllerWithConfig` to the callbacks.
3. A `Dockerfile` on a distroless base, non-root, read-only root filesystem.

Proof: the image builds and the binary starts against a kubeconfig, logs that it
is watching the kind, and exits cleanly on SIGTERM.

## Milestone 5: the install

1. `deploy/` with namespace, serviceaccount, rbac, deployment and a
   kustomization, matching the RBAC table in [packaging.md](packaging.md).
2. `chart/` with the same objects templated, `image.digest` in values, and a
   README saying `deploy/` wins where they disagree.
3. `.github/workflows/release.yaml` copied from kuport's and renamed, with the
   digest grep and the semver guard intact.

Proof: a `v0.0.1` tag produces four assets, and the rendered manifest contains
`@sha256:`.

## Milestone 6: it works on the test cluster

Every step here is on the walzen test cluster, and every command that changes
the cluster is the admin's to run.

1. Install the unit, as [integration.md](integration.md) describes.
2. Point one canary's claim at a VolumeRestore.
3. Watch the claim bind, the app start, and the pool.

| Check | Expected |
| --- | --- |
| `kubectl get pvc` in the app's namespace | the claim Bound, and no `volsync-*-dest` claim beside it |
| `kubectl get zfsvolume -A -o custom-columns='NAME:.metadata.name,SNAP:.spec.snapname'` | the app's volume with an empty `snapname` |
| `zfs list -t all -o name,used,refer,origin -r zfspv-pool` on the node | no clone and no snapshot for that volume |
| delete the claim | it is recreated, refilled, and the app comes back with its data |
| the mover pod | admitted by Kueue, like every other mover |

The third row is the project. Record the numbers beside the same measurement
taken on a volume still using the snapshot path, so the infrastructure
repository's documentation can state a magnitude rather than a mechanism.

## Milestone 7: the infrastructure repository

Follow [integration.md](integration.md): the module, the unit, the component

## What would make this project wrong

Say so rather than working around it:

- the library's prime claim cannot be given the app's storage class or node, so
  the volume lands somewhere the pod cannot follow
- VolSync's Direct restore into an empty claim leaves it in a state the app
  cannot use, for example wrong ownership that the mover's security context
  cannot fix
- the rebinding leaves a PersistentVolume that zfs-localpv does not recognise as
  its own, so deleting the claim later fails to clean up the dataset
- the restore of a large volume takes long enough that the library's own
  timeouts fire before a mover finishes

The fourth is the most likely of the four and the first to test, because a
fifty gigabyte restore is the case this project exists for.
